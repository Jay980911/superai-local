# UI/UX Pro Max — 方法论与能力边界

> 本文件说明引擎「为什么这么算」「算法的能力边界」「典型失效模式」。
> 对标 nextlevelbuilder/ui-ux-pro-max-skill，但定位为**本地化、离线、可审计的设计智能方法论引擎**，
> 而非联网抓取或审美终审工具。

---

## 一、整体架构

```
描述 / 关键词
   │
   ├─ BM25 检索 (跨维度)
   │     ├─ product  → 产品类型推理规则（推荐 pattern / style / 配色 / 字体 / 反模式）
   │     ├─ style    → 50+ UI 风格库
   │     ├─ palette  → 161 确定性调色板
   │     ├─ font     → 57 字体搭配
   │     ├─ chart    → 25 图表类型
   │     ├─ pattern  → 24 落地页结构
   │     └─ guideline→ 85 条优先级 UX 指南
   │
   └─ generate（设计系统生成器）
         产品匹配 → 风格推导 → 调色板匹配(色相感知) → 字体匹配 → 组装 7 段式设计系统
```

设计立场：**「AI 不随机选设计，而是按产品类型科学匹配」**。
引擎的每一步都是可解释、可复现的——这与原项目「以搜索数据库驱动决策」的核心理念一致。

## 二、BM25 检索原理

标准 Okapi BM25：

```
score(D,Q) = Σ_{t∈Q} IDF(t) · (f·(k1+1)) / (f + k1·(1−b + b·|D|/avgdl))
IDF(t)     = ln(1 + (N − df(t) + 0.5) / (df(t) + 0.5))
```

- `k1 = 1.5`（词频饱和），`b = 0.75`（文档长度归一）。
- 文档 = 各条目的 name + keywords + aliases + 相关字段拼接成的 token 序列。
- 中文按字符 n-gram 粗切（正则 `[a-z0-9一-鿿]+`），英文按词；停用词（the/of/for…）剔除。
- 检索是**确定性**的：同一查询永远返回同一结果，便于审计与回归。

**能力边界**：BM25 是词汇重叠模型，不理解语义。
「 luxury spa 」与「高端水疗」不会跨语言命中；需中英文分别表达。
查询越具体（带行业词 + 格式词），匹配越准。

## 三、调色板生成算法（161 个）

调色板不是人工抄录的 161 条死数据，而是由**确定性算法**生成，保证可复现、可审计：

1. **色相分布**：`hue = (i × 137.508) mod 360`（黄金角），使 161 个色相均匀铺满色环、不聚类。
2. **配色方案**：5 种（analogous / complementary / triadic / monochromatic / split-complementary）轮转。
3. **情绪→饱和度/明度**：12 种情绪关键词映射到饱和度(28–80)与明度(40–50)偏好
   （如 Vivid=72/Cyber=80/Premium=38/Muted=28）。
4. **角色推导**：
   - `primary` = 主色相的中饱和中明度；
   - `secondary` = 方案第二色相，明度略升；
   - `accent(CTA)` = 主色相高饱和，确保与背景拉开；
   - `bg/surface/border` = 极低饱和、极高明度（亮色模式）；
   - `text` = 经 `contrast_ratio` 自动选深/浅，保证与背景满足 WCAG。
5. **暗色变体**：同一套色相推导 `bg=#0d..` 级别，重新选文字色。

所有 hex 由 `hsl_to_hex` 计算（HSL→RGB 标准公式，无第三方依赖）。
`contrast_ratio` 严格按 WCAG 2.x 相对亮度公式计算，输出介于 1.0–21.0。

**为什么用算法而非硬抄 161 条**：可审计、零授权风险、可随需求扩展；
代价是单条调色板不具备「品牌叙事」（如「星巴克绿」这种命名语义），但这恰是方法论引擎应有的克制——
它给的是**可验证的色彩关系**，不是某品牌的私有资产。

**调色板匹配（hue-aware）**：`generate` 解析产品类型的 `color_mood` 文本，
用 `_HUE_MAP`（blue→220、green→140、gold→45 …）抽取目标色相，
在 161 个调色板中选取基础色相最接近者（情绪命中再加权），
从而让「botanical green」真正落到偏绿调色板，而非随机。

## 四、设计系统生成器的推导链

`generate(description, stack, mode, name)`：

1. **产品匹配**：BM25 在 `PRODUCT_TYPES` 检索 → 取置信分最高的 `category`。
2. **风格推导**：取该类别 `style_priority[0]` 作为推荐风格，取其完整规格（keywords/best_for/effects/anti_patterns）。
3. **调色板匹配**：解析 `color_mood` → hue-aware 选取（见上）。
4. **字体匹配**：解析 `type_mood`（如「Inter / Sora / IBM Plex Sans」）→ 在 57 组搭配中精确匹配，命中即返回；
   未命中则 BM25 回退到首组。输出 Google Fonts `css2` 引入链接。
5. **组装输出**：7 段式
   - 页面结构 Pattern
   - UI 风格 Style（+ 关键词/适用/效果）
   - 色彩系统 Colors（`mode` 下 7 角色 hex + 正文对比度 + 方案/情绪）
   - 字体系统 Typography（标题/正文 + 引入链接）
   - 关键效果 Effects
   - 反模式清单 Anti-Patterns（该行业专属规避项）
   - 交付前检查清单 Pre-Delivery QA（取全体 P0 指南作为门禁）

## 五、UX 指南的优先级模型

85 条指南标注三级优先级：

| 级别 | 含义 | 示例 |
|---|---|---|
| **P0 阻断** | 上线前必须过；不过则不可用/不合规 | 对比度≥4.5:1、键盘可达、移动优先、单主 CTA |
| **P1 重要** | 显著影响体验/转化 | 跳过链接、表单 label、reduced-motion、srcset |
| **P2 增强** | 打磨项 | 暗色模式、底部导航、tabular-nums |

`audit` 子命令与 `generate` 的 QA 清单均以 P0 为硬门禁。

## 六、典型失效模式（诚实声明）

1. **语义盲区**：BM25 只认词面重叠。「高端」「premium」需分别表达；跨语言不互通。
2. **调色板无品牌语义**：算法调色板是色彩关系，不是品牌资产；落地需人工校正品牌色。
3. **对比度静态估算局限**：`generate` 给出的是「文字 vs 背景」单一关系对比度；
   实际界面还有小字、禁用态、叠加层，**必须用真机/axe 等工具实测**，本引擎不替代。
4. **`audit` 启发式粗判**：仅做正则级静态检查（img 缺 alt、缺 lang、outline:none 无替代等），
   会**漏报**（算不出真实对比度）也可能**误报**（有文本的按钮被保守跳过）。
   关键无障碍项务必人工 + 专用工具复核。
5. **产品类型规则为策展种子集**：覆盖主流行业 ~30 类，未穷尽 161 子类；
   长尾行业（如特定监管金融子项）匹配可能落到相邻类别，须人工确认。
6. **不下终局结论**：引擎输出是「推荐起点」，不是审美终审或合规认证。

## 七、与同系技能的边界

| 技能 | 关注点 | 本技能的关系 |
|---|---|---|
| `frontend-design` | Anthropic 设计语言「设计宪法」 | 本技能更偏「搜索数据库驱动的具体选型」 |
| `web-design-guidelines` | 149 条 a11y/UX 规则审计 | 本技能含 85 条指南 + 生成器，互补 |
| `vercel-react-best-practices` | Next.js 性能/规范 | 本技能在 `stacks` 维度对其做轻量覆盖 |

四者合起来构成「视觉宪法 → 可访问性审计 → 性能规范 → 设计系统选型」的前端质量闭环。
